NGINX Ingress Migration Tool

NGINX Ingress Controller (nginx/kubernetes-ingress) is actively maintained and is the recommended migration target.
Version reference: This tool is based on Ingress-NGINX v1.15.1 (final release) and NGINX Ingress Controller v5.7.0.

Overview

This interactive guide helps you migrate from the community-maintained Ingress-NGINX controller (kubernetes/ingress-nginx) to NGINX Ingress Controller (nginx/kubernetes-ingress). It covers 130+ annotation mappings, ConfigMap key translations, and CRD migration examples across three pages, listed in the sidebar:

  • Getting started — Background on why to migrate, CRD overviews, installation, and a migration checklist
  • Ingress-NGINX config analyzer — Paste an Ingress manifest and get automatic migration suggestions with ready-to-use YAML
  • Reference guide — Complete annotation and ConfigMap mapping tables with side-by-side examples

Why migrate?

The two controllers take fundamentally different approaches to configuring NGINX in Kubernetes.

  • Ingress-NGINX is annotation-driven — it relies on annotations and ConfigMap keys to customize NGINX. These are opaque strings with no schema validation — a single Ingress resource may carry dozens of annotations as unstructured key-value pairs.
  • NGINX Ingress Controller is CRD-native — it uses Custom Resource Definitions (VirtualServer, Policy, TransportServer) as its primary config model, providing structured, schema-validated YAML with IDE autocompletion.

While NGINX Ingress Controller still supports annotations for common settings, CRDs unlock capabilities that annotations cannot express:

  • Schema validation — Kubernetes validates CRD fields at apply time, catching misconfigurations before they reach NGINX
  • Structured configuration — Nested YAML objects replace long annotation strings, making complex routing, traffic splitting, and security policies readable and maintainable
  • Reusability — Policies (rate limiting, auth, WAF) are defined once and attached to any number of routes
  • Layer 4 support — TransportServer CRDs handle TCP/UDP workloads that annotations cannot express
  • IDE and tooling support — CRD schemas enable autocompletion, linting, and documentation in editors and CI pipelines

Phased migration strategy

Rather than performing a "big bang" cutover, F5 recommends a phased migration that allows you to validate each workload before decommissioning the community controller. Both controllers can run side-by-side in the same cluster using separate IngressClass resources.

  1. Deploy side-by-side — Install NGINX Ingress Controller alongside the community controller using a distinct IngressClass such as nginx-nic (see Install alongside the community controller). Existing traffic is unaffected.
  2. Migrate service-by-service — Update each Ingress resource's ingressClassName to point to the new controller. Convert annotations as described in the reference guide, validate routing and TLS behavior, and promote to production before moving on to the next service.
  3. Decommission — After all workloads have been migrated and validated, remove the community controller deployment, its IngressClass, and any unused ConfigMaps.
Tip: Use the Ingress-NGINX config analyzer to process each Ingress manifest during step 2. It flags unsupported annotations and generates the equivalent NGINX Ingress Controller configuration.

Install alongside the community controller

Both Helm charts name their class nginx by default, and an IngressClass name can belong to only one controller. Give NGINX Ingress Controller its own class:

Helm (example)

helm install nginx-ingress oci://ghcr.io/nginx/charts/nginx-ingress \
  --set controller.ingressClass.name=nginx-nic \
  --set controller.config.name=nginx-config \
  --set controller.enableSnippets=true \
  --set controller.enableTLSPassthrough=true

Keep only the flags your Ingresses need:

  • controller.config.name — The examples on this page write the ConfigMap nginx-config, the name the manifests install. The chart names it after the release instead (nginx-ingress for this command) unless this is set, and NGINX Ingress Controller reads only the ConfigMap its -nginx-configmaps flag names, so keys written to any other one are silently unused.
  • controller.enableSnippets — Off by default. With it off, NGINX Ingress Controller rejects any resource that carries a snippet, so configuration-snippet, server-snippet and every mapping that becomes a snippet fail. Snippets are copied as written: directives from modules the community image included, such as more_set_headers (headers-more) and Lua, do not exist in NGINX Ingress Controller and fail the configuration reload.
  • controller.enableTLSPassthrough — Off by default. ssl-passthrough becomes a TransportServer on the built-in tls-passthrough listener, which exists only with this flag.
  • controller.enableCertManager — Off by default. cert-manager HTTP-01 challenges for a VirtualServer's host pass its HTTPS redirect and authentication only with this flag (v5.7.0 and later); on an Ingress they do without it. The community controller exempted /.well-known/acme-challenge by default.
  • controller.enableTopologyAwareRouting — Off by default, like the community controller's --enable-topology-aware-routing, and new in v5.7.0. With it on, each controller pod sends traffic to the endpoints in its own zone, or on its own node, when the Service sets spec.trafficDistribution (or the older service.kubernetes.io/topology-mode: auto), falling back to every ready endpoint otherwise.
Note: The NGINX Ingress Controller documentation covers this in Run multiple Ingress controllers and the ingress-nginx migration guide.

Gateway API

The community project recommends that new users adopt a Gateway API implementation. NGINX Gateway Fabric is the NGINX implementation of the Gateway API, and ingress2gateway converts Ingress resources to it (--providers=ingress-nginx for community annotations). This tool covers the move to NGINX Ingress Controller, which keeps the Ingress API.

CRDs summary

NGINX Ingress Controller uses Custom Resource Definitions (CRDs) to extend Kubernetes with NGINX-specific configuration. CRDs provide type-safe, validated configuration that goes beyond what standard Ingress annotations can offer.

VirtualServer CRD

The primary CRD for configuring HTTP/HTTPS load balancing. It replaces Ingress resources and provides advanced traffic management capabilities with full validation.

  • Traffic Splitting: Route percentages of traffic to different backends for canary/blue-green deployments
  • Content-Based Routing: Route based on headers, cookies, arguments, or variables
  • Path Rewriting: Modify request URIs with regex support before forwarding to backends
  • Error Pages: Custom responses for specific HTTP error codes
  • Request/Response Headers: Add, modify, or remove headers in transit
  • Health Checks: Active health monitoring of upstream servers (NGINX Plus)
  • Session Persistence: Cookie-based sticky sessions

VirtualServerRoute CRD

Enables delegation of route configuration to different namespaces. Allows teams to manage their own routing rules while maintaining centralized control over the domain.

  • Cross-Namespace Routing: Reference services in different namespaces
  • Path Delegation: Delegate path prefixes to other teams/namespaces
  • Independent Updates: Teams update routes without modifying the parent VirtualServer
  • Access Control: Limit which namespaces can define routes for a host

Policy CRD

Reusable security and traffic policies that can be attached to VirtualServers or specific routes. Policies enable consistent security controls across multiple applications.

  • Rate Limiting: Limit request rates by IP, header, or custom key
  • Access Control: IP allowlists and denylists
  • Basic Auth: Username/password authentication via htpasswd
  • JWT Validation: Validate JSON Web Tokens (Plus)
  • OIDC: OpenID Connect sign-in, through the built-in OIDC module or NGINX JavaScript (Plus)
  • API Key Auth: Authenticate via API keys in headers/query
  • mTLS: Client certificate verification (ingress) and backend TLS (egress)
  • WAF: F5 WAF for NGINX web application firewall (Plus)

TransportServer CRD

Configures TCP/UDP load balancing for non-HTTP protocols. Essential for databases, message queues, gaming servers, and other Layer 4 applications.

  • TCP Load Balancing: MySQL, PostgreSQL, Redis, custom TCP services
  • UDP Load Balancing: DNS, RADIUS, gaming protocols
  • TLS Passthrough: Pass encrypted traffic directly to backends
  • Health Checks: TCP/UDP health monitoring (NGINX Plus; ignored on NGINX Open Source)
  • Session Persistence: IP hash-based session affinity

GlobalConfiguration CRD

Cluster-wide listeners for NGINX Ingress Controller: the TCP, UDP and HTTP ports that TransportServers and VirtualServers reference by name.

  • TCP/UDP Listeners: Define ports for non-HTTP traffic
  • HTTP Listeners: Extra HTTP or HTTPS ports a VirtualServer selects in spec.listener

Installing CRDs

CRDs can be installed via Helm or manually using manifests, depending on your deployment method. See the NGINX Ingress Controller installation docs for full instructions.

Helm (example)

If you install NGINX Ingress Controller via Helm, CRDs are included automatically. To ensure they are enabled:

helm install nginx-ingress oci://ghcr.io/nginx/charts/nginx-ingress --version 2.8.0 --set controller.enableCustomResources=true

The controller.enableCustomResources flag is true by default. If you previously disabled it, re-enable it to use CRD resources. See the Helm installation guide for details.

Manifests (example)

If you deploy using manifests, install CRDs manually before deploying the controller:

kubectl apply -f https://raw.githubusercontent.com/nginx/kubernetes-ingress/v5.7.0/deploy/crds.yaml

Replace the version number with your target controller version. See the manifest installation guide for the full step-by-step process.

Note: The crds.yaml file contains all CRDs (VirtualServer, VirtualServerRoute, Policy, TransportServer, GlobalConfiguration) in a single manifest.

Migration checklist

Progress is saved in your browser.
  • Install CRDs via Helm (controller.enableCustomResources=true) or manifests (deploy/crds.yaml)
  • Install with its own IngressClass (controller.ingressClass.name=nginx-nic), and turn on controller.enableSnippets or controller.enableTLSPassthrough if your Ingresses need them
  • Review the defaults that change (response buffering, HTTP/2, HSTS, keepalive, timeouts, load balancing) and set the ones that matter in nginx-config
  • Review annotation mappings — not all nginx.ingress.kubernetes.io/ annotations have a direct nginx.org/ equivalent (see NGINX mappings)
  • Map rewrite-target annotation to nginx.org/rewrite-target (not nginx.org/rewrites)
  • Migrate ConfigMap keys that differ between controllers (see ConfigMap mappings)
  • Convert HSTS ConfigMap keys to nginx.org/hsts annotations for per-Ingress control, or an hsts Policy on a VirtualServer (v5.6.0+)
  • Convert server-tokens ConfigMap key to nginx.org/server-tokens annotation
  • Convert access control annotations to Policy CRD (accessControl)
  • Convert authentication annotations to Policy CRD (apiKey, basicAuth, externalAuth, jwt, oidc, oidcNative)
  • Convert canary/traffic splitting to VirtualServer splits/matches
  • Convert mTLS annotations to ingressMTLS/egressMTLS policies
  • Convert CORS annotations to the cors Policy CRD via nginx.org/policies (v5.4.0+), falling back to snippets only where needed
  • Convert custom error pages to nginx.org/custom-http-errors with a spec.defaultBackend (v5.6.0+), or VirtualServer errorPages
  • Convert header manipulation to VirtualServer requestHeaders/responseHeaders
  • Convert rate limiting annotations to Policy CRD (rateLimit)
  • Convert redirect annotations to VirtualServer action.redirect
  • Convert session affinity annotations to VirtualServer upstream sessionCookie
  • Convert SSL passthrough to TransportServer CRD
  • Convert TCP/UDP services to TransportServer CRD
  • Replace ssl-redirect with nginx.org/ssl-redirect (not the deprecated ingress.kubernetes.io/ssl-redirect)
  • Verify snippets (configuration-snippet, server-snippet) use only directives NGINX Ingress Controller ships — no more_set_headers or Lua
  • Test in staging environment
  • Update monitoring and alerting

The analyzer on this page works on what you paste. nic-migrate runs the same engine from a terminal, across every Ingress in a directory or read straight from a running cluster. It loads the mapping database out of this site's own source rather than keeping a second copy, so it cannot drift from the tables in the reference guide. It is not distributed as a download — clone the repository for this site and run it with Node 18 or newer, with nothing to install.

node tools/nic-migrate/nic-migrate.js report -f ./manifests

Generate manifests

Merges those results into resources you can apply: one VirtualServer per host carrying every route and backend, with Policies referenced, TLS preserved, and the namespace kept. --target ingress instead keeps your Ingress resources and rewrites their annotations.

node tools/nic-migrate/nic-migrate.js convert -f ./manifests --validate

Neither command drops anything silently: where a construct has no equivalent on the target you choose, it is named rather than omitted. New in NGINX Ingress Controller
                

                    
                    
                    
                    
                

                
Fewer snippets, and the Secrets you already have: proxy-http-version maps to nginx.org/proxy-http-version or a VirtualServer upstream's proxy-http-version instead of a snippet, and HTTP/2 to upstreams joins it. gRPC turns HTTP/2 on per host with nginx.org/http2 or spec.http2, with or without TLS. opentelemetry-trust-incoming-span maps to the otel-trace-context ConfigMap key, and the community's ewma load balancing to least_time last_byte, now on NGINX Open Source. Custom error pages and upstream Host on Ingress: Two community annotations now have direct Ingress equivalents: nginx.org/custom-http-errors serves intercepted errors from the Ingress's spec.defaultBackend, and nginx.org/upstream-vhost sets the Host header sent upstream. A new hsts Policy CRD sets HSTS on a VirtualServer, including preload on request. With NGINX Plus, the new oidcNative Policy runs OpenID Connect in the built-in module and attaches to Ingress through nginx.com/policies.

                
ExternalAuth Policy and expanded Policy CRDs on Ingress: A new externalAuth Policy CRD replaces the community's generic auth_request annotations (auth-url, auth-signin, auth-snippet) — the headline migration win of this release. The ingressMTLS, egressMTLS, and waf (Plus, via nginx.com/policies) Policy CRDs can now also be attached directly to Ingress resources. New direct annotation mappings arrived for proxy-redirect-from/proxy-redirect-to, alongside a new inline nginx.org/add-header (plus nginx.org/add-header-inherit) for response header injection.

                
Policy CRDs on Ingress objects: Policy CRDs (e.g. accessControl, cors) can now be referenced directly from Ingress resources using the nginx.org/policies annotation — no VirtualServer required. NGINX Ingress Controller
# The community order — deny, then allow, then deny all — as one location
# snippet. An Ingress cannot place a Policy after its snippet: an
# nginx.org/policies allow list renders at server level, and a snippet
# deny in the location would stop the location inheriting it.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
  annotations:
    nginx.org/location-snippets: |  # denylist-source-range + whitelist-source-range
      deny 10.1.2.3;
      allow 10.0.0.0/8;
      allow 172.16.0.0/12;
      deny all;

                                

                                
Allow plus deny: When a resource references an allow and a deny Policy, NGINX Ingress Controller applies only the allow list. The community controller checked the deny list first, so an address inside an allowed range could still be denied. NGINX takes the first allow or deny that matches, and a location with rules of its own inherits none from its server, where a Policy in spec.policies or nginx.org/policies renders. So never pair a location-snippet deny with such a Policy: it lifts the allow list for every client (verified on nginx 1.31.7: an address outside it got 200). Put the denies first in the same location instead, as above. Denied ranges that overlap no allowed range need nothing, because allow-only already blocks them. Snippets need the controller's -enable-snippets flag.

                                
New in v5.4.0: AccessControl policies can now be referenced directly from Ingress resources using the nginx.org/policies annotation. This is the simplest migration path — you stay on Ingress resources.

#    list when a resource references allow and deny Policies,
#    so the deny list is not a Policy.

metadata:
  name: my-app-access-control

      - "172.16.0.0/12"
---

#    renders in the location after its snippet, so the deny comes first.

  name: my-app
spec:
  host: app.example.com
  upstreams:
    - name: backend
      service: backend-svc
      port: 80
  routes:

      policies:

      location-snippets: |  # denylist-source-range

      action:

New in v5.5.0: The externalAuth Policy CRD can be referenced directly from Ingress resources using the nginx.org/policies annotation. This is the simplest migration path — you stay on Ingress resources. auth-url is split into authURI (path) and authServiceName (<namespace>/<service>). The community's auth-method, auth-response-headers, auth-cache-duration, auth-cache-key, auth-proxy-set-headers, auth-request-redirect, and auth-signin-redirect-param annotations have no dedicated Policy fields — express these through authSnippets when needed. The analyzer sets it to the sign-in path's parent directory, or to the path itself when that parent is /, as for /login here.

Under CRD-first the analyzer emits errorPages and warns that annotation-first, which keeps the annotation, suits this Ingress better.

Without a spec.defaultBackend the annotation does nothing. The default-backend annotation names only a Service, so set the port in spec.defaultBackend to the one that Service serves on; the community controller used its first port.

To pin a client to the canary, route it with a cookie or header match (canary-by-cookie or canary-by-header), as above. The sessionCookie feature is available in both NGINX Open Source and NGINX Plus.

NGINX Ingress Controller reads the one its -nginx-configmaps <namespace>/<name> flag names: nginx-config in the manifests, and with Helm the release's name unless controller.config.name sets it (see Install alongside the community controller).
